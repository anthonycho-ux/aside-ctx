# aside-ctx

面向 AI 对话的内容寻址上下文存储。

---

## 一句话概括

一个用 Go 编写的 Sidecar 程序。它监视 AI 会话日志，发现超过 1KB 的工具执行结果后，会用 SHA-256 哈希存储，并用一个简短的句柄引用替换内联文本。下一次对话轮次中，AI 看到的将是一个 187 字节的句柄，而不是 45KB 的终端输出。相同内容始终产生相同句柄——自动去重。

提示开销降低约 65%。内容寻址。仅追加。零依赖。

---

## 为什么做这个

迈克尔·刘易斯的《大空头》里有个场景。对冲基金经理史蒂夫·艾斯曼意识到整个次贷市场建立在一个谎言之上。他不是通过阅读某一份贷款的细则发现的——他是通过看整体数据发现的：他注意到无文件证明贷款和全文件证明贷款的违约率*完全相同*。这意味着文件流程只是演戏。系统背负着没人需要的死重，却假装那是结构性的。

我也有过这样的艾斯曼时刻。只不过我看的不是抵押贷款证券，而是 AI 对话。

每次我和 AI 代理对话——Claude、GPT，无论哪个——模型都要重新读取该对话中产生的每一个工具执行结果。每一个 JSON 数据块。每一条终端输出。每一份三周前让它读过后就再也没翻过的文件。我测量过：对话内容的 71.2% 是已经看过的输出。AI 把大部分注意力预算花在阅读没人会再看第二遍的内容上。

这不是一个 bug。这是基于聊天的代理工作方式中内建的设计决策。对话记录是唯一的记忆。一切永远保留——或者直到上下文崩溃，信号随噪音一起消失。

解决方案简单到令人尴尬。你不需要携带全部文本。你只需要携带一个指纹——SHA-256 哈希——只有当你真正需要阅读原文时才去获取。相同的内容总是产生相同的指纹，所以同一段终端输出出现在三个不同的对话中，也只存储一次。

我用 Go 构建它，因为这是一个系统问题，而不是数据科学问题。一个 Sidecar。零依赖。一个在 :9876 上的 HTTP API。优化器监视会话文件，发现超过 1KB 的数据块，存储它们，用句柄替换内联文本。AI 知道如何解析句柄——因为我把指令放进了它的系统提示中。

结果：提示开销降低约 65%。AI 花更少时间重读昨天的垃圾，花更多时间解决今天的问题。一个 60KB 的记忆文件压缩到 13KB。一段 45KB 的终端输出变成 187 字节的引用。

内容寻址存储本身并不新鲜。Git 用它。IPFS 用它。新鲜的是将它应用到 AI 中成本最高的部分——上下文。

我把它叫做 aside-ctx，因为它存在于 AI 的旁边(aside)，而不是内部。一个上下文的 Sidecar。

## 工作原理

```
┌──────────┐   会话日志    ┌────────────┐  POST /store  ┌──────────┐
│ AI 代理  ├─────────────►│  优化器    ├─────────────►│ aside-ctx│
│ (Claude) │              │  (监视器)  │              │ (:9876)  │
└──────────┘              └────────────┘              └────┬─────┘
      ▲                                                   │
      │          ┌────────────────────────┐               │
      └──────────┤ [stored in aside-ctx]  │◄─────────────┘
                 │ handle=sha256:abc...   │  GET /resolve/{h}
                 │ digest="build OK"      │
                 │ size=45721             │
                 └────────────────────────┘
```

优化器每 10 秒轮询会话 JSONL 文件。当发现大于 1KB 的工具执行结果时，将内容发送到 aside-ctx 的 `/store` 端点。守护进程计算 SHA-256，检查是否已存在（去重），存储数据块，返回句柄。优化器重写会话文件——45KB 的终端输出变成一行：

```
[stored in aside-ctx] tool=bash handle=sha256:a1b2c3... digest="build succeeded" size=45721
```

下一个对话轮次中，AI 看到句柄。如果需要完整内容——比如调试构建失败——通过 `curl http://127.0.0.1:9876/resolve/sha256:a1b2c3...` 获取。如果不需要，直接跳过。上下文窗口保持精简。

## 数据

| 指标 | 之前 | 之后 |
|--------|-------|-------|
| 提示开销 | 100%（基准） | ~35% |
| 45KB 终端输出 | 45,721 字节内联 | 187 字节（句柄） |
| 60KB 记忆文件 | 60,408 字节 | 13,409 字节（索引） |
| 去重 | 无 | 自动 (SHA-256) |
| 检索 | 始终加载 | 按需获取 |

---

## 快速开始

```bash
# 启动守护进程
./aside-ctx --port 9876 --store ~/.aside-ctx

# 存储内容
curl -s -X POST http://127.0.0.1:9876/store -d '{"content": "..."}'

# 解析句柄
curl -s http://127.0.0.1:9876/resolve/sha256:abc...

# 统计信息
curl -s http://127.0.0.1:9876/stats
```

## 为什么用 Go

这是一个系统问题：文件 I/O、HTTP、进程管理、紧密循环。Go 提供用于并发会话监控的 goroutine、无需框架即可处理 HTTP 的标准库，以及没有运行时依赖的单一二进制文件。守护进程、优化器、内存索引器——全在 `go build` 之内。
