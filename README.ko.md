aside-ctx: AI 대화 맥락을 위한 콘텐츠 주소형 저장소
---

## 한 줄 요약

Go로 만든 사이드카입니다. AI 세션 로그를 감시하다가 1KB 넘는 도구 실행 결과를 발견하면 SHA-256 해시로 저장하고, 본문 대신 짧은 핸들 참조로 바꿔치기합니다. 다음 턴이 되면 AI는 45KB 터미널 덤프 대신 187바이트짜리 핸들만 보게 됩니다. 같은 내용은 항상 같은 핸들이 나오니까 중복 저장도 없습니다.

프롬프트 오버헤드를 ~65% 줄였습니다. 콘텐츠 주소형. 추가 전용. 의존성 제로.

---

## 왜 만들었는지

마이클 루이스의 *빅 쇼트*에 나오는 장면이 있습니다. 헤지펀드 매니저 스티브 아이즈먼은 서브프라임 모기지 시장 전체가 거짓말 위에 세워졌다는 걸 깨닫습니다. 그는 단 한 건의 모기지 약관을 읽어서 알게 된 게 아닙니다. 데이터를 전체로 봤기 때문에 알게 된 겁니다. 서류를 전혀 요구하지 않은 모기지의 연체율과 서류를 완벽히 갖춘 모기지의 연체율이 *똑같다*는 사실을 발견한 겁니다. 그 차이가 없다는 건 서류라는 절차 자체가 연극이라는 뜻입니다. 시스템은 아무도 필요로 하지 않는 죽은 무게를 짊어지고 있었습니다.

저도 그런 순간이 있었습니다. 모기지 증권이 아니라 AI 대화를 분석하다가 마주쳤습니다.

AI 에이전트와 대화할 때마다 — Claude든 GPT든 — 그 모델은 지금까지 해당 대화에서 생산된 모든 도구 실행 결과를 다시 읽어야 합니다. 모든 JSON 블롭. 모든 터미널 덤프. 3주 전에 읽어보라고 시켰고 그 뒤로 한 번도 들춰보지 않은 파일까지. 직접 측정했습니다. 대화 내용의 71.2%가 이미 한 번 본 출력물이었습니다. AI는 주의력 예산의 대부분을 아무도 다시 필요로 하지 않을 내용을 읽는 데 쓰고 있었습니다.

이건 버그가 아닙니다. 채팅 기반 에이전트가 작동하는 방식에 이미 짜여진 설계 결정입니다. 대화 기록이 유일한 기억입니다. 모든 것이 영원히 남습니다. 아니면 컨텍스트 붕괴가 일어나서 신호까지 노이즈에 묻혀 사라질 때까지요.

해결책은 창피할 정도로 단순합니다. 전체 텍스트를 들고 다닐 필요가 없습니다. 지문(SHA-256 해시)만 들고 다니고, 실제로 읽어야 할 때만 원본을 가져오면 됩니다. 같은 내용은 항상 같은 지문을 만들어내니까, 같은 터미널 출력이 세 개의 다른 대화에 나타나도 한 번만 저장됩니다.

Go로 만들었습니다. 이건 데이터 과학 문제가 아니라 시스템 문제이기 때문입니다. 사이드카. 의존성 없음. :9876에 하나의 HTTP API. 옵티마이저가 세션 파일을 감시하다가 1KB 넘는 블롭을 발견하면 저장하고, 본문을 핸들로 바꿉니다. AI가 핸들을 어떻게 처리해야 하는지는 시스템 프롬프트에 명령어를 넣어서 가르쳐줬습니다.

결과: 프롬프트 오버헤드가 ~65% 줄었습니다. AI는 어제의 쓰레기를 다시 읽는 대신 오늘의 문제를 푸는 데 더 많은 자원을 씁니다. 60KB 메모리 파일이 13KB로 줄었습니다. 45KB 터미널 덤프가 187바이트 참조가 됩니다.

콘텐츠 주소형 저장소 자체는 새롭지 않습니다. Git이 쓰고, IPFS가 씁니다. 새로운 점은 AI에서 가장 비용이 많이 드는 것, 즉 맥락(context)에 이 방식을 적용했다는 겁니다.

aside-ctx라고 이름 지었습니다. AI의 안(aside)에 함께 살아가기 때문입니다. 맥락을 위한 사이드카입니다.

## 구조

```
┌──────────┐   세션 로그    ┌────────────┐  POST /store  ┌──────────┐
│ AI 에이전트├──────────────►│ 옵티마이저 ├─────────────►│ aside-ctx│
│ (Claude)  │               │ (감시자)   │               │ (:9876)  │
└──────────┘                └────────────┘               └────┬─────┘
      ▲                                                      │
      │         ┌──────────────────────────┐                 │
      └─────────┤ [stored in aside-ctx]    │◄───────────────┘
                │ handle=sha256:abc...     │  GET /resolve/{h}
                │ digest="build OK"        │
                │ size=45721               │
                └──────────────────────────┘
```

옵티마이저는 10초마다 세션 JSONL 파일을 폴링합니다. 1KB보다 큰 도구 실행 결과를 발견하면 aside-ctx의 `/store` 엔드포인트로 내용을 보냅니다. 데몬이 SHA-256을 계산하고, 이미 있는 내용인지 확인하고(중복 제거), 블롭을 저장하고 핸들을 반환합니다. 옵티마이저가 세션 파일을 다시 씁니다 — 45KB의 터미널 출력이 한 줄로 바뀝니다:

```
[stored in aside-ctx] tool=bash handle=sha256:a1b2c3... digest="build succeeded" size=45721
```

다음 대화 턴에서 AI는 핸들을 봅니다. 전체 내용이 필요하면 — 예를 들어 빌드 실패를 디버깅해야 한다면 — `curl http://127.0.0.1:9876/resolve/sha256:a1b2c3...` 로 가져옵니다. 필요 없으면 그냥 넘어갑니다. 컨텍스트 윈도우는 가볍게 유지됩니다.

## 수치

| 항목 | 전 | 후 |
|--------|-------|-------|
| 프롬프트 오버헤드 | 100% (기준) | ~35% |
| 45KB 터미널 출력 | 45,721바이트 인라인 | 187바이트 (핸들) |
| 60KB 메모리 파일 | 60,408바이트 | 13,409바이트 (인덱스) |
| 중복 제거 | 없음 | 자동 (SHA-256) |
| 검색 | 항상 로드 | 필요시에만 |

## 빠른 시작

```bash
# 데몬 시작
./aside-ctx --port 9876 --store ~/.aside-ctx

# 내용 저장
curl -s -X POST http://127.0.0.1:9876/store -d '{"content": "..."}'

# 핸들 확인
curl -s http://127.0.0.1:9876/resolve/sha256:abc...

# 통계
curl -s http://127.0.0.1:9876/stats
```

## 왜 Go인가

이건 시스템 문제입니다: 파일 I/O, HTTP, 프로세스 관리, 타이트한 루프. Go는 동시 세션 감시를 위한 고루틴, 프레임워크 없이 HTTP를 처리하는 표준 라이브러리, 런타임 의존성이 없는 단일 바이너리를 제공합니다. 데몬, 옵티마이저, 메모리 인덱서 — 모두 `go build` 하나로 끝납니다.
